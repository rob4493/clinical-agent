# Private Live embed activation

Status: implemented for operator-only Deploy Preview preparation; not live-verified.
Public production is rejected in server code even if every opt-in is set. Existing
Endo evidence, claims, cases and uploads remain disconnected. No new IAM key, SDK
or dependency is needed. A separate client-owned RSA signing key is required by
IBM Embed Security; an IAM API key is not that signing key.

## Written activation sequence

1. Review the existing diff and verify all automated checks. Do not merge or deploy
   main. Use only the already authorized isolated feature-branch preview workflow.
2. Generate or obtain the dedicated embed signing key below. Register its public
   half with IBM. Configure the private half only as a server-side Functions secret.
3. Inspect the existing Live agent's effective tools, collaborators and connections.
   Establish server-enforced denial of all tenant tools/collaborators reachable by
   this JWT User principal, including other agents, and verify it using
   authoritative permissions and a non-side-effecting denial check. Model promises
   and hidden UI controls are not evidence. Do not send clinical text to test it.
4. Verify the protected preview's Netlify team-login context and operator allowlist,
   atomic Blob storage, privacy/retention and IBM usage controls. Check that direct
   Function URLs reject other visitors too. Password-only protection is insufficient.
5. Set the exact preview-only configuration listed below after these checks. Their
   acknowledgement flags record operator verification; flags do not perform it.
6. Start AI conversation inside Endo. Only the operational session request reaches
   Netlify. Only after a successful issuer response does the official script load.
7. In the real IBM composer, send the previously approved nonclinical two-turn probe:
   ask it to remember the fictional name Blue Lantern, then ask what name was given.
   Inspect actual responses for continuity without saving message bodies or tokens.
   Record success/failure and latency only. Do not use patient or clinical scenarios.
8. End the session and set the preview kill switch true. Public activation remains
   a separate review, never a follow-on toggle. No production settings are changed.

## Manual signing-key preparation

Do not run key generation in this repository. Use approved private operator storage
or a secrets manager. No real key was generated by this implementation. The exact
OpenSSL commands documented by IBM are:

```text
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out private.pem
openssl rsa -in private.pem -pubout -out public.pem
```

Use a restricted directory outside the checkout; `private.pem` is PKCS#8. Protect its
access permissions. Never paste it into chat, source, a CLI argument, VITE variables,
build logs or a committed environment file. Existing `*.pem` and `*.key` ignore rules
remain intact. Those rules are a backup, not permission to put keys in the checkout.

Calculate the public-key fingerprint without printing the private key:

```text
node -e "const fs=require('node:fs'),c=require('node:crypto');const k=c.createPublicKey(fs.readFileSync(process.argv[1]));process.stdout.write(c.createHash('sha256').update(k.export({type:'spki',format:'der'})).digest('hex'));" public.pem
```

If a public key is already registered, first locate its matching server-held private
key and reuse it where permitted. Do not overwrite another integration's key. A
replacement needs a coordinated tenant-impact review and explicit rotation plan.

IBM console: open the existing instance, Profile > Settings > Embed Security.
Set Security On, paste only the contents of `public.pem` into Public key, and save
using the console's displayed control. Review tenant-wide impact before saving.
Do not disable security or change the existing agent/version. No OBO user payload
is used, so this application does not require IBM's encryption key or SSO tokens.
Keep the supplied Live orchestrationID, hostURL and agentId unchanged. The runtime
uses a dedicated Endo mount instead of replacing React's `root`.

The issuer uses trusted context.deploy to require an unpublished Deploy Preview
and context.user for the unexpired allowlisted operator. It pins the exact configured
deploy-preview-4 alias and PR ID, which survive a rebuild. Netlify does not provide
CONTEXT or DEPLOY_ID as standard Function-runtime environment variables. The old
ORCHESTRATE_EMBED_PREVIEW_DEPLOY_ID setting is retired and must not be used as an
activation requirement; it made redeploy configuration circular. No built-in values
are manually overridden. New PRs require deliberate origin/PR repinning. Token
ownership remains bound to the actual trusted immutable context.deploy.id, so a
token from an earlier rebuild cannot be renewed on the new rebuild.
Netlify documents context.user for team-login-protected hosted Functions; it is not
available in local CLI emulation. Do not inject a fake user into deployed code.

## Bounds and lifecycle

POST /api/v1/embed-session accepts exactly {"action":"start"}, or a renewal with
only action and token. It accepts no clinical fields, supplied subject or context.
Origin, URL, method, streamed body and operator identity are checked before signing.
Errors are fixed codes without exception text. The function deadline is five seconds.
No IBM/IAM request occurs in the issuer, imports, health, readiness or discovery.

JWTs use RS256 with a minimum 4096-bit RSA key and the pinned public fingerprint.
The subject is random. Payload contains only sub, iat, nbf, exp and jti. Tokens live
at most 120 seconds; original issuance time fixes the total session at ten minutes,
shortened by operator expiry and the approved test window. Renewal verifies the
signature and immutable operator ownership and cannot extend the session window.
No token is written to storage or an application log. Operational Blob tickets are
in EndoEmbeddedPreviewQuota, separate from production conversation reservations.
One atomic initial session per UTC day is allowed across all previews/operators.
Failures may consume capacity; there is no reset/delete endpoint. Renewal does not
create another session. Request-rate limiting complements this admission limit.

IMPORTANT: token/session admission is not a hard per-message spending limit. The
browser talks directly to IBM after authorization. Require an IBM-enforced bounded
test allowance before enabling issuance. Ending the UI or disabling renewals does
not revoke a token IBM already accepted; it can remain valid up to 120 seconds.

The loader uses init(configuration), top-level token, layout.customElement and
chatOptions.onLoad. Renewal sets authTokenNeeded event.authToken and invokes
updateAuthToken(). Expiry stops renewal and tears down the widget. StrictMode,
repeated starts, unmount and local-fallback selection cancel bootstrap and detach
handlers. Only one SDK lease is allowed; it remains held while initialization and
destroy settle. Loader initialization has a twenty-second UI deadline. An SDK that
never settles requires page refresh rather than opening a competing instance.

Cancellation aborts Endo's token transport and invokes IBM loader.destroy(). No
supported per-inference AbortSignal API was established for the browser SDK. Do
not claim destroy cancels an already running IBM request, deletes retained history,
or guarantees SDK-owned storage is cleared. Review real SDK storage/logging and
retention in the protected preview. Removing a script does not itself cancel every
browser fetch. SDK code has same-page privileges; lack of automatic case projection
is not a sandbox against vendor code reading the DOM. No on-send case hook is added.
